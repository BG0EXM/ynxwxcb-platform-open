# 伊宁县委宣传部部务工作平台

> 版本：**V1.8.0**（更新日期：**2026-10-20**）

面向县级党委宣传部的内部部务工作平台，开源免费，可自部署。

- 🗂️ 收文管理（呈批单/传阅登记卡/热敏标签打印）、征求意见（跨单位回函协同）、材料下发（免密查收存证）、考勤点到（含迟到）、请假管理、公车报备、值守排班、工作日历、会务管理、公共资料、大事记、每周工作总结、加班管理、年休假管理、常委管理、通讯录
- ⚙️ Go + Vue3 + SQLite 单二进制部署，零运维
- 🔒 可配置的角色-功能权限矩阵（48个权限点），数据范围按科室/本人隔离
- 🛡️ 国家保密安全防线：全链路四维涉密智能审查（Word/PDF/扫描件OCR），严防非涉密网络违规涉密流转
- 🧱 应用级防火墙 (WAF)：多重URL解码防绕过、大请求内存防放大、安全阻断页与真实审计日志留痕
- 📜 操作日志审计（仅管理员），关键操作、WAF拦截、涉密违规留痕、中文可读
- 🛡️ 登录按用户名+IP 限流、失败锁定、令牌可即时吊销，密码至少 8 位
- 🔑 首次登录强制修改默认密码，保障账号安全
- 📄 各模块台账一键导出 Excel，支持 A4 打印与 80×50mm 热敏标签
- 📊 列表接口分页，数据量大时依然流畅
- ⚡ 前端按需加载，首屏体积控制在 ~228KB
- 🌐 完全离线可部署，Nginx / Caddy 均可，支持 IPv6

## 功能模块

| 模块 | 说明 |
|---|---|
| 收文管理 | 上级来文登记、呈批单/传阅登记卡/热敏标签生成打印、文件退回管理 |
| 征求意见 | 公文草案发起、全县单位范围管控、外链免密分发、各单位在线填报反馈与盖章件上传、防篡改锁定、台账导出与回函一键打包ZIP下载 |
| 材料下发 | 非回执类政务公文免密码下发、受邀单位实名经办人查收签收、阅读次数统计、查收进度追踪与台账导出 |
| 考勤点到 | 管理员晨会手工点到、月度/年度统计与打印 |
| 请假管理 | 年假及各类假期登记、假条一键打印（按请假天数自动匹配审批流程）、统计与 Excel 导出 |
| 公车管理 | 车辆基础信息（车架号/保险等）、用车报备、派车单打印 |
| 会务管理 | 会议录入、一键生成公文通知文本、匿名免密报名链接、参会登记（单位限额控制）、签到单导出 |
| 公共资料 | 共享资料发布与阅读 |
| 通讯录 | 按部门/姓名查询 |
| 值守排班 | 日历视图当天值守（至21:00收文）、可标记县委大院排班 |
| 工作日历 | 全屏大日历（按月/按年展示），各科室在格子中添加要做的工作，跨天连续显示，列表展示，Excel 导出（可单科室/全部） |
| 大事记 | 各科室每月重大事项，按年汇总整个宣传部并导出 Word（仅管理员） |
| 每周工作总结 | 各科室录入本周重点工作，管理员可增删改全部，导出 Word 汇总（仅管理员） |
| 加班管理 | 加班记录录入、加班统计与补休管理（8 小时=1 天），Excel 导出（仅管理员） |
| 年休假管理 | 管理员配置每人每年年休假天数，已休联动请假，普通用户只读（仅管理员可配置） |
| 常委管理 | 常委大事记，按年/月展示，录入/修改/删除，导出 Word（仅管理员） |
| 系统管理 | 用户、角色、部门管理（添加/改名/删除） |
| 权限管理 | 角色-功能权限矩阵，48 个权限点按角色勾选（仅管理员） |
| 操作日志 | 关键操作/登录/导出/WAF拦截/涉密阻断留痕，按模块/动作/日期/关键词查询（仅管理员） |

> 各模块台账（用车报备/请假/考勤/排班/收文/征求意见/材料下发）均支持 Excel 导出。

## 更新日志

### V1.8.0（2026-10-19）

**全系统安全与数据防线深度治理 · 公开链接令牌化 · 全站 UI 视觉升级与手机端重构**

**⚠️ 升级必读（生产环境）**
- 数据库自动升级到 v20，升级前务必先执行 `deploy/backup.sh` 备份。
- 会务、征求意见、材料下发的公开链接改为随机令牌，**升级前发出的旧链接全部失效**，正在进行的事项需要在后台重新“复制链接”或“一键通知”。
- 乡镇通讯员（reporter）角色默认收回“征求意见管理 / 材料下发管理”权限，如确有需要，可在权限管理中手动开启。
- `config.json` 的 `admin.password` 改为只在管理员账号不存在时生效，不再每次启动覆盖界面上改过的密码；找回密码需临时设置 `admin.force_reset: true`。
- 前置 nginx/Caddy 时，请设置 `server.trust_proxy: true`、`server.host: "127.0.0.1"`，并更新 nginx 配置中的 `X-Forwarded-For`。
- 只要服务器上的 `config.json` 里仍有 `admin.password`，升级后第一次启动不会再改动管理员密码，这是预期行为。

**🗂️ 附件与文件安全（数据丢失类）**
- 上传目录配置为相对路径时，下载附件 404，孤儿清理还会把所有附件当成无引用文件删掉 → 附件路径统一存为“相对上传目录”，下载、预览、打包、删除、清理共用同一套解析；启动时自动把历史路径规范化。
- 数据恢复到其他目录后，旧的绝对路径会被当成孤儿文件删除 → 按路径末段在当前上传目录中找回文件。
- 孤儿清理直接永久删除文件 → 改为先移入 `uploads/.trash/日期/`，30 天后才删除；引用大面积解析失败或待清理比例异常时，整轮停止清理。
- 删除公共资料会连带删除同编号收文的附件 → 只清理本资料自己的附件，并在事务提交后再删文件。
- 征求意见、材料下发保存时，照单接收客户端传来的文件路径，可以借此公开下载或连带删除任意附件 → 只接受本人上传、类型匹配、未被其他记录占用的附件，并在保存时绑定。
- 公开端回函可以引用其他单位的文件，管理员重置时会把对方的文件一起删掉 → 回函按“征求事项 + 单位”分目录存放，只能引用本单位目录下的文件；每个单位最多上传 20 个文件。
- 更新征求意见或材料下发后，被替换的旧文件仍留在磁盘上 → 保存后同步清理。
- 公共资料详情接口返回服务器上的物理路径 → 改为返回带鉴权的下载地址。
- `/uploads/` 直读接口不检查附件权限，路径大小写不同就能绕过敏感目录限制 → 套用与附件下载相同的权限校验；隔离区目录禁止访问。

**🔐 账号认证与权限**
- 删除用户后编号会被复用，被删管理员未过期的登录令牌可能在新用户身上“复活” → 用户表和附件表不再复用编号；身份、角色、状态一律以数据库为准，不再采信令牌里携带的角色。
- 默认密码的强制修改只在前端判断，可以绕过 → 改由服务端强制，改密前只允许访问个人信息、修改密码和退出登录。
- 修改密码时输入超过 72 字节的密码，系统提示成功，实际账号再也无法登录 → 超长密码直接拒绝，所有出错情况都会正确报错；新密码不能设成默认密码。
- 每次启动都会用配置文件里的密码覆盖管理员密码，管理员账号还写死了角色编号 → 只在账号不存在时创建，角色按“管理员”身份查找。
- 登录锁定只按用户名计次，别人故意输错几次就能把 admin 锁住 → 改为按“用户名 + IP”锁定；记录失败次数的内存数据会定期清理。
- 账号被禁用时，还没校验密码就提示“已禁用”，等于告诉别人这个账号存在 → 改为先校验密码，再提示禁用。
- 管理员可以禁用自己，修改用户时漏传状态会把账号误禁用，没有“至少保留一个管理员”的保护 → 三项均已补上。
- 非管理员但持有“用户管理”权限的人，可以给自己提权、修改或删除管理员 → 只有系统管理员能授予管理员角色，或修改、重置、删除管理员账号。
- 登录令牌放在网址参数里也能使用，令牌可能被写进日志 → 取消这种方式，只接受请求头携带的令牌；JWT 校验限定算法、要求有过期时间、校验签发方。
- 默认密码账号曾以通讯员身份拥有征求意见、材料下发管理权限 → v20 迁移从通讯员角色收回这两项权限。
- 全局搜索和工作台不检查功能权限，普通用户能看到收文标题和通讯录电话 → 每个搜索类别分别校验对应权限。

**🌐 公开填报页（会务 / 征求意见 / 材料下发）**
- 公开链接用连续数字编号，外人可以逐个试出全部会议、草案和材料 → 改为 128 位随机令牌，旧数字链接一律失效。
- 会务报名请求里自带会议编号就能绕过链接 → 会议只认链接里的令牌。
- 知道单位名称就能修改、替换其他单位已报的参会人员 → 单位首次报名时签发编辑凭证，之后修改、移除、取消都必须带上凭证。
- 公开材料下发页返回经办人的完整手机号和 IP → 姓名、电话一律脱敏，不再返回 IP。
- 公开征求意见页能看到其他单位的意见内容和内部文件编号 → 只返回是否已答复，去掉内部路径。
- 材料下发回执可以被他人覆盖 → 重复查收只累加查收次数，保留首位经办人；增加手机号格式校验。
- 截止时间格式无法识别时，事项永远不会截止 → 保存时校验格式，无法识别的一律按已截止处理。
- 公开反馈接口不限制请求大小 → 只对两个上传接口放开大小限制，反馈内容限 64KB 并限制各字段长度。
- 在公开页切换单位后，上一单位的回函、意见、联系人仍留在表单里 → 切换单位时清空表单。

**🛡️ 防火墙与涉密检测**
- 防火墙从 `X-Forwarded-For` 最左一段取 IP，客户端可以伪造，从而绕过限流 → 只在连接来自本机或内网代理时才采信代理头，优先取 `X-Real-IP`，其次取 `X-Forwarded-For` 最右一段。
- 普通中英文正文会被误判为 SQL 注入 → 收紧 SQL 关键词规则，中文正文和普通英文句子不再误拦。
- 防火墙可以被注释混淆、JSON 转义、伪装上传请求、PATCH/DELETE 请求绕过 → 均已覆盖检测。
- 拦截页显示的 IP 没有转义，拦截日志也没有限频 → IP 转义输出；同一 IP 每 10 秒最多记 1 条，全局每分钟最多 60 条。
- 极小的图片文件可以声明超大分辨率，Word 文档条目过多，都可能耗尽内存 → 图片先检查尺寸，超过 4000 万像素跳过识别；Word/Excel 解压总量限 50MB、条目限 500 个；上传内容超出 8MB 的部分写入磁盘，不再全部留在内存。
- 文字识别（OCR）没有并发上限，大量上传可以把 CPU 占满 → 全局最多同时 2 个识别任务。
- PDF 转图片超时后，残留的临时图片含有公文内容 → 超时或失败后立即清理。
- 超过 30MB 或无法解析的 Word/Excel 文件直接放行，不做检测 → 完整检测，无法解析的一律拒绝上传。
- 压缩包、图片逐字节匹配关键词，大文件约有 1%~6% 被误判为涉密 → 压缩和图像格式不再做逐字节兜底匹配。
- 文件名含“保守国家秘密法”等字样的学习资料被锁定会话 → 加学习宣传类词组白名单，只作用于文件名检测。
- 文字识别程序会从临时目录加载，存在被替换的风险 → 只从项目和程序所在目录加载，且文件不能被他人修改。

**⚙️ 业务逻辑**
- 公车报备的冲突检测和保存不在同一事务里，并发提交会撞车；冲突查询出错时还会放行 → 检测与保存放进同一个事务，出错一律拒绝。
- “使用中”的车辆不能预约其他时段，状态提示文字也和实际含义对不上 → 只有维修中和已报废的车辆禁止报备，提示文字已更正。
- 请假可以登记 31 天只扣 0.5 天，按小时请假还能跨天 → 天数不得超过起止日期跨度，按小时请假只能单日且不超过 8 小时，单次请假最长 366 天。
- 编辑跨年的年休假时，不检查新年度余额 → 编辑时同样按日历比例分摊到两个年度分别核算。
- 改了请假类型，考勤记录里的类型不跟着变；删除请假时会误改管理员手工标记的考勤 → 类型变化同步更新；只回退由请假联动产生的考勤标记。
- 普通用户可以随意修改过去月份的请假 → 过去月份的请假只有管理员能改、能删，页面上显示“已锁定”。
- 工作日历的列表和导出不按科室隔离 → 普通用户只能看到本科室的日历。
- 会务“不参加”、移除人员、删除加班、收文传阅登记存在并发漏洞 → 均改为在事务内复核，或用单条语句原子完成。
- 考勤点到、会议时间、车辆信息缺少校验 → 已补齐格式和取值范围校验。
- 考勤档案里年休假有两套统计口径，数字对不上 → 统一采用余额卡片的那套计算口径。
- 用户管理左侧按科室筛选不起作用 → 后端已支持按科室过滤。

**🗄️ 数据库与性能**
- 并发写入时偶发“登记失败” → 事务开启时立即获取写锁（`_txlock=immediate`）。
- 导出 Excel 和工作台“本周值班”的时间少 8 小时 → 导出统一换算为北京时间；服务配置固定北京时区，程序内置时区数据。
- 按年月筛选的查询用不上索引，数据多了会变慢 → 改为能走索引的写法（`GLOB`）。
- 列表每页条数没有上限，不分页的列表会一次读出全部数据 → 每页最多 100 条，不分页列表最多 2000 条。
- 导出时遇到空字段会悄悄跳过整行 → 空值按 0 处理，读取失败的行会记录日志。
- 多处查询没有检查读取过程中的错误 → 已补齐，查询类接口出错时直接返回错误，不再给出不完整的数据。
- 新增 v20 数据库迁移：公开链接令牌、默认密码强制修改标记、会务单位编辑凭证表、收回通讯员两项权限、存量附件绑定所属记录。

## 技术栈

- 后端：**Go 1.26**（标准库 HTTP）+ SQLite（纯 Go，无 CGO）
- 前端：**Vue 3 + Element Plus + Pinia + Vue Router + Vite**
- Excel 导出：excelize/v2
- 部署：主程序 + 静态资源目录，反向代理（Nginx / Caddy 均可），systemd 托管

## 目录结构

> 下面描述的是**源码仓库**的结构。部署到服务器时，只需取出「可执行文件 + static 文件夹」两样（见下方「部署」章节）。

```

## 部署

系统由两部分组成，**都要放到服务器上**：
1. **主程序** `ynxwxcb-server`（编译出的可执行文件）
2. **static 文件夹**（前端网页文件）

> ⚠️ **【重要】服务端涉密审查 OCR 与 PDF 视觉组件提示（强烈推荐）**：
> 本平台在服务端全面集成了四维文档涉密审查引擎。对于普通的 Word (`.docx`) 及电子文本 PDF，系统通过内置纯 Go 解码引擎完成内容解构，**服务器无需安装任何三方组件即可离线检测**。
> 若您的业务需要支持**扫描件公文图片**以及**扫描式纯图片 PDF 公文**的离线光学文字审查（OCR），需在 Linux 生产服务器上安装通用 Tesseract OCR 引擎及 Poppler 工具库（系统启动后将自动智能探测识别）：
> - **Ubuntu / Debian**：
>   ```bash
>   sudo apt-get update && sudo apt-get install -y tesseract-ocr tesseract-ocr-chi-sim tesseract-ocr-chi-tra poppler-utils
>   ```
> - **CentOS / RHEL / Rocky Linux**：
>   ```bash
>   sudo yum install -y epel-release && sudo yum install -y tesseract tesseract-langpack-chi_sim tesseract-langpack-chi_tra poppler-utils
>   ```
> - **组件分工**：
>   - `tesseract-ocr` + `tesseract-ocr-chi-sim` + `tesseract-ocr-chi-tra`：负责扫描件图片离线 OCR 识别，已内置简繁字库互补与繁简自动规整；
>   - `poppler-utils`（内置 `pdftoppm` 命令）：负责将纯扫描式 PDF 页面高保真渲染为图像送入 OCR 审查，彻底杜绝扫描公文规避检测。
> - **说明**：未安装上述组件时，系统启动时将打印提示日志，并自动无缝退化为“文件名 + Word XML 全文/页眉/页脚 + PDF 原始文本流/CMap”模式，常规协同业务不受影响。

部署后服务器目录结构如下：

```
/opt/ynxwxcb/
├── ynxwxcb-server        # 可执行文件
├── static/             # 前端页面文件夹（与可执行文件同级）
├── config.json         # 配置文件
└── data/               # 运行时自动生成（数据库/上传文件）
```

**部署有两种方式，任选其一：**

---

### 方式一：本地编译好后上传（推荐，最简单，服务器不用装环境）

> 适合小白，你只需要在自己电脑上做两步，然后把两个东西传到服务器。

**第 1 步：在自己电脑上编译出可执行文件**

在电脑上打开终端（命令行），进入项目 backend 目录：

```bash
cd backend
CGO_ENABLED=0 GOOS=linux GOARCH=amd64 go build -o ynxwxcb-server ./cmd/server
```

> 前提：电脑上装了 Go 语言环境。没装的话，看文末「常见问题」里的安装方法。
> 如果你连 Go 都不想装，也可以找已编译好的 `ynxwxcb-server` 文件直接用。

**第 2 步：把两个东西传到服务器**

需要上传到服务器的就这两样（放进同一个目录，比如 `/opt/ynxwxcb/`）：

| 文件/文件夹 | 说明 |
|---|---|
| `ynxwxcb-server` | 编译出的可执行文件 |
| `static/` | 前端页面文件夹（用仓库 `backend/static/` 里的） |

**第 3 步：在服务器上运行**

```bash
cd /opt/ynxwxcb
./ynxwxcb-server -config config.json
```

> 用 systemd 托管可开机自启，见 `deploy/systemd/ynxwxcb.service`。

---

### 方式二：在服务器上直接编译（懂行的用，服务器要装 Go）

> 适合在服务器上有 Go 环境、且把源码传到服务器的人。

```bash
# 1. 把整个项目源码上传到服务器（含 backend、frontend 等）
# 2. 进入 backend 目录编译
cd backend
CGO_ENABLED=0 GOOS=linux GOARCH=amd64 go build -o ynxwxcb-server ./cmd/server

# 3. 把 static 文件夹放到与 ynxwxcb-server 同一目录，然后运行
./ynxwxcb-server -config config.json
```

---

> **关键点**：后端在**运行目录**下找 `static/` 文件夹，所以无论用哪种方式，`ynxwxcb-server` 和 `static/` 必须放在**同一目录**。仓库里的 `backend/static/` 已帮你准备好前端页面，直接把它作为服务器上的 `static/` 文件夹用即可。

**什么时候需要重新构建前端？**
只有当你想**修改前端界面**（换背景图、改文案、改界面布局）时，才需要用 `npm run build` 重新生成 `static/` 文件夹。不想改前端就完全不用管。

完整部署见 [docs/DEPLOY.md](docs/DEPLOY.md)（Nginx）或 [docs/DEPLOY-CADDY.md](docs/DEPLOY-CADDY.md)（Caddy）。

## 数据库升级

从旧版本升级到新版本，**只需替换主程序 `ynxwxcb-server` 后重启**，无需手动操作数据库。

- 程序启动时会自动检测数据库版本（`schema_versions` 表），按版本号顺序执行未执行的迁移
- 新增表 / 加字段 / 改结构都通过迁移自动完成，**已有数据完整保留**
- 升级前建议先备份：`bash backup.sh`（备份到 `/opt/ynxwxcb-backup/`）

> 迁移逻辑见 `backend/internal/database/database.go` 的 `migrations` 列表，每次版本升级只需追加一个迁移函数。

## 常见问题

**Q1：电脑没装 Go，怎么编译？**
- Windows：去 https://go.dev/dl 下载安装包，装完重启终端
- Linux：`sudo apt install golang`
- 如果实在不想装 Go，可以让已编译好的人给你一份 `ynxwxcb-server` 文件直接上传

**Q2：`CGO_ENABLED=0 GOOS=linux GOARCH=amd64` 是什么？**
- 表示"编译出 Linux 64 位系统能运行的程序"（不管你在 Windows 还是 Mac 上编译）
- 照抄这行命令即可，不用理解每个参数

**Q3：上传到哪里？**
- 可执行文件和 static 文件夹放**同一个目录**，建议 `/opt/ynxwxcb/`

**Q4：static 文件夹哪来的？**
- 直接用仓库里的 `backend/static/` 文件夹，整文件夹复制到服务器

**Q5：页面打开是 404 或空白？**
- 99% 是 static 文件夹没放对位置或没传上去
- 确认服务器上 `ynxwxcb-server` 和 `static/` 在**同一目录**
